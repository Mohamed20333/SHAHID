01 / THE PROBLEM

The question attendance systems avoid.

“How will you stop a student registering attendance on behalf of an absent friend?” Manual attendance proves that a name was marked — not necessarily that the person engaged in the session.

01

Manual entry

Useful as the administrative attendance signal, but inherently proxyable.

02

Independent evidence

Short recall questions tied to real lecture content provide a separate engagement signal.

03

Human review

Repeated divergence creates a risk flag for instructor review — never an automatic penalty.

02 / THE MECHANISM

Separate presence from engagement.

A friend can tick a name once. The smart layer asks a different question: did the student actually engage?

01 / START

Session begins and attendance is marked manually.

02 / PULSE

Recall question fires at the end of the session.

03 / REPEAT

A second content-linked check fires one week later.

04 / SCORE

Responses become an engagement score per student.

05 / REVIEW

Attendance and engagement divergence can trigger a review flag.

03 / SMART LAYER

Risk scoring, made transparent.

The implemented model uses explicit weights. The threshold is a review trigger, not a disciplinary verdict.

Low engagement

05 / SECURITY & PRIVACY

Security is part of the product.

  • Passwords hashed with scrypt.
  • JWT verification is HS256-only.
  • Professor dashboards enforce ownership authorization.
  • No biometric images stored by default.
  • Risk flags are for human review.
  • On-device escalation path transmits only a signed pass/fail result.
  • The prototype uses SQLite locally; PostgreSQL is the intended production target.
  • Automated tests cover authentication, authorization, escalation, weekly caps and JWT integrity.
HONEST ENGINEERING

Evidence → signal → review.

Not a claim of perfect attendance security. A transparent mechanism designed around what the prototype actually builds and tests.
